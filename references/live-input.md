# 把触屏操作送进远端实时会话

前置阅读 [webrtc-realtime.md](webrtc-realtime.md)（会话怎么建起来）、
[debugging.md](debugging.md)（取证纪律）。

**一句话结论：输入不通时，先怀疑自己发出去的那几个数字和单位，最后才怀疑协议。**
这条链路每一环都是静默失败——网关不报错、画面照常播、JS 异常只进日志。最后定案的
两个真根因，一个在坐标单位，一个在自己误删的一行代码，**都不在协议里**。

## 两条输入通道，两套坐标单位

同一份信令连接上并存两种输入协议，**坐标单位不同**，混用就静默失效：

| 通道 | op 码 | 拼装格式 | 坐标单位 |
|---|---|---|---|
| 移动端触摸 | `1` down / `2` move / `3` up / `4` cancel / `8` tap | `"<op> x y id"` | **视频像素** `0..videoWidth` / `0..videoHeight` |
| PC 鼠标 | `100` down / `101` up / `102` move / `103` wheel | `"100 btnType posType x y state"` / `"102 posType x y state"` | **65535 归一化百分比** |
| PC 键盘 | `104` keydown / `105` keyup | `"104 keyCode keyName state"` | — |

判定"该用哪套"看的是远端**容器里跑的是什么**，不是"我们这边有没有接鼠标"：
容器里是安卓手游就只能是触摸协议，端游才是鼠标协议。

### 实测 A/B：同一控件，只换单位

目标是远端登录卡片上一个手机号输入框，同一个 `id=0`，都是 `down` 紧接 `up`、中间无
`move`（与官方单击路径同构）。唯一变量是发出的坐标：

| page 坐标 | 视频像素 | 实际发出的 cmd | 远端反应 |
|---|---|---|---|
| (230, 87) | (622, 235) | `1 31846 21390 0`（65535 百分比） | **无任何反应** |
| (222, 87) | (601, 235) | `1 601 235 0`（视频像素） | **279ms 后网关下发 `cmd "1 …"`（要求弹输入框）** |

另两条百分比对照同样零反应：命中"进入游戏"按钮的 `8 32819 45784`、命中右上角的
`8 46848 10832`。

为什么百分比"看起来合理却完全失效"：远端按像素解释（推断：`31846 > 1280`、
`21390 > 720`，被钳到右下角），所有点击落到同一角落，**不报错、无 NAK、画面继续播**。
"钳到角落"是推断（真机只能观测到零反应），但"发百分比零反应 / 发像素有反应"是实测的。

### 代码里必须同时保留两套换算

```js
/* 移动端触摸：视频像素，四舍五入并 clamp。单位错了就是全部点失效。 */
export const PX = (x, w) => { var v = Math.round(Number(x) || 0), m = Number(w) || 1280;
  return v < 0 ? 0 : (v > m ? m : v); };
export const PY = (y, h) => { var v = Math.round(Number(y) || 0), m = Number(h) || 720;
  return v < 0 ? 0 : (v > m ? m : v); };

/* PC 鼠标：65535 归一化百分比。别拿它去发 1/2/3。 */
export const NX = (x, w) => Math.ceil((65535 * x) / (w || 1280));
export const NY = (y, h) => Math.ceil((65535 * y) / (h || 720));
```

**必须**在每个调用点写清用的是哪套：`tap()/down()/move()/up()` 只准用 `PX/PY`，
`mouseDown()/mouseUp()/mouseMove()` 只准用 `NX/NY`。函数名本身就要能区分通道，
不要取 `sendTouch(x,y)` 这种两组单位都能塞进去的名字。

## `pageX/pageY` 已经是子矩形内的局部坐标

视频区常常只是画布的一块子矩形（本项目是 `{x: 243, y: 0, w: 473, h: 266}`，左边 243
是侧栏、右边 244 是控制栏）。触摸事件回调里的 `pageX/pageY` **已经扣掉了这个子矩形的
原点**，再减一次 `VIDEO.x` 就整体偏移。

### 三点采样验证法（十分钟能做完，不要靠猜）

在面板物理坐标上点三个已知点，读日志里的 `pageX/pageY`，验证这个关系：

```text
pageX == 逻辑x - VIDEO.x      （横向）
pageY == 逻辑y - VIDEO.y      （纵向）
```

本项目实测（`VIDEO.x = 243`）：

| 面板物理 tap | 反算逻辑坐标 | 日志里的 page | 横向验证 |
|---|---|---|---|
| (111, 480) | (480, 4) | (237, 3) | `480 - 243 = 237` ✅ |
| (207, 480) | (300, 4) | (57, 3) | `300 - 243 = 57` ✅ |
| (140, 378) | (582, 33) | (339, 32) | `582 - 243 = 339` ✅ |

三个点全部满足同一条线性关系（**截距为 0**），就说明 `pageX` 是 stage 内坐标、
**不要再减原点**。若三点算出来的截距是一个固定的非零值，那个值就是漏减/多减的原点。

纵向同理（`pageY - VIDEO.y`），只是注入点的物理坐标和回调上报的 `pageY` 之间有
±1px 的取整误差，别拿单点当判据，看三点是否**都**偏同一个值。

### 事件对象只有这些字段

Falcon 的触摸事件对象实测只暴露：`pageX`、`pageY`、`screenX`、`screenY`、
`identifier`、`changedTouches`（外加 `touches`/`targetTouches` 的同类结构）。
**没有** `clientX`/`offsetX`/`offsetY`。用 `Number(t.clientX)` 得到 `NaN`，再被
`if (!isFinite(x)) x = 0` 兜底成 0，结果**每个点都落到左上角且一行错误都不打**。
"非法值兜底成 0"必须同时配一条日志，否则它会把字段名错误悄悄吞掉。

## ★ 最坑的一类失败：JS 异常只进日志，不阻断画面

真实案例，值得完整读一遍。

清理临时诊断日志时，`onTS`（`touchstart` 回调）里的这一行被连带删掉了：

```js
onTS: function (e) {
  var ts = (e && e.changedTouches) || [];   // ★ 被误删的就是这一行
  if (!this.touchReady()) return;
  for (var i = 0; i < ts.length; i++) this.touchDown(ts[i]);
}
```

后果链：

1. 每次 `touchstart` 都在 `ts.length` 处抛 `ReferenceError: ts is not defined`；
2. 异常被 Vue 的事件包装吞掉，只进 `console.warn/error`（设备上只有它落盘）；
3. **`down` 一帧都没发出去**；`touchIds` 从未被填充，`touchend` 里
   `id === undefined` → `continue`，**`up` 也被跳过**；
4. 表现：画面在播、手指在点、远端毫无反应。

当时的现象与"坐标单位错"、"协议猜错"、"必须走 DataChannel"**完全一样**，排查方向
因此被带偏很久——去查 65535 百分比、去接鼠标协议、去评估自研 SCTP，全是伪问题。

两条规则：

- **触摸回调的第一行必须是取事件数组**。改动 `onTS` 前后都要肉眼确认这一行还在。
- **异常必须显式上报到 UI**，哪怕只是一行红字。只写 `console.warn` 是不够的：
  它不会让任何人看见，而画面正常会继续骗你"一切都好"。

```js
onTS: function (e) {
  var ts = (e && e.changedTouches) || [];      // 第一行，不许动
  try {
    if (!this.touchReady()) return;
    for (var i = 0; i < ts.length; i++) this.touchDown(ts[i]);
  } catch (err) {
    this.errText = '输入异常: ' + ((err && err.message) || err);   // ★ 必须上屏
  }
}
```

## 不要用"远端回显"验证点击生效

把全部下行 `op=input` 解密后统计 cmd 首段（4000+ 条，跨多次开局的全量，不是抽样）：

```text
0  : 4133     我方 "0 <ms>" 心跳的回显（1:1 echo，条数能对上）
23 : 50       网关下发的「当前前台 Activity」通知
8  : 24       网关下发：横竖屏切换
2  : 24       网关下发：收键盘
18 : 24       网关下发：光标锁
1  : 1        网关下发：要求弹输入框（唯一一条，是它主动发的）
```

**网关对我们发上去的 `1`/`2`/`3`/`8` 一律不 echo**。开局时那组 `8 0` / `2` / `18 0`
是网关自己的控制帧，出现时机固定，**不是**我们 up/tap 的回声。

所以："回显里没有 `1`/`3`，说明 down/up 没发出去"是**错误推论**。同理，回显里有
`2` 也不代表 move 送达。要判断输入是否生效，只能看**界面语义变化**：远端是否弹出了
输入框、是否切换了 Activity、截图里是否出现了新元素。

## 截图 diff 不能当判据

云画面本身是动态的。实测：**什么都不做**，在同一局里间隔 10 秒连拍 6 帧，
相邻两帧的 `np.abs(a-b).sum(2) > 25` 像素数分别是：

```text
682645  611544  717289  662095  574499      （基准 921600）
```

也就是"不动也在变"74%，量级和"点了一下"完全重叠。拿 diff 大小当判据，**必然**得到
假阳性或假阴性。

反例：登录页是完全静止的 UI，连续两帧 diff = **0 / 921600**；点它的关闭按钮后
diff = **918168 / 921600 = 99.63%**——这种"整屏换内容"的量级才是真变化。

正确做法：

- 先测基线：**不发任何输入**，连拍两帧算 diff，确认基线是多少；
- 判据用语义：截图里是否出现预期的新控件/新界面；
- 更硬的判据是**下行控制帧的时序**（例如点击输入框后 279ms 网关主动下发 `cmd "1 …"`）。

## 看门狗：别在已结束的会话上做输入测试

native 侧有个看门狗：JS 每 120ms 调一次 poll 刷新 `last_poll_ms`，超时就把管线拆掉、
把 KMS 平面还回去（否则小程序被切走后视频平面会永远盖住系统 UI）。

```c
/* PenCG/native/csrc/cgmedia/cm_media.c:33 —— 注释与值不一致，以值为准 */
#define WATCHDOG_MS 60000
```

这段注释写着"阈值取 6 秒"，实际值是 **60000 = 60 秒**。文档和代码注释都可能过期，
**读 `#define` 的数字**。

与输入测试的关系：小程序被切走、弹系统键盘、长时间息屏时 QuickJS 定时器会停摆，
poll 断了之后会话就被拆了。**之后所有点击都落在一个已结束的会话上**，现象是"点了
完全没反应"，与坐标错的症状一模一样。任何输入测试前先确认会话还活着：

```text
# 日志里的 session id 还在不在、有没有 "media loop exit" / "session torn down"
```

WS 层的存活心跳是另一件事：本项目每 10 秒发一条 `cmd "0 <Date.now()>"`，网关 1:1
回显，回显里的 `0` 数量就是"链路还通"的计数。（官方在 DataChannel 上是 1 秒一次；
我们借 WS 发，1 秒一次会把日志和轮询队列灌满，所以降到 10 秒，会话活性不受影响。）

## 输入模式切换会静默丢事件

起播时官方会发一条 `cmd "25 <keymouse|tochscreen>"` 声明输入模式。实测：

- 切到 `keymouse` 之后，PC 鼠标事件（`100`/`101`/`102`）**被远端全部丢弃**，点击零响应
  （项目内的实测记录）；
- 因此本项目无论跑手游还是端游，**固定只发 `tochscreen`**，从不发 `keymouse`。

端游那条路径我们只观测到过一次"大范围重绘"，**未能稳定复现**，所以这里不给端游的
推荐配置，只给"不要把模式切到 keymouse"这一条硬结论。

**两个不要动的地方**：

1. 官方拼写就是 `tochscreen`（少一个 `u`）。**不要"纠正"成 `touchscreen`**——网关按
   字面量比对，改一个字母就整条失效。
2. 换模式之前先把手上所有 touch point 收干净（发 `up` 或 `cancel`）。模式切换时远端会
   重置槽位，我们这边 `touchIds` 不清空的话，后续 `move`/`up` 会带着过期 id 发过去。

## 远端文本输入的握手

远端需要文字输入时不是"发一个字符串"，而是一套小握手（全部来自官方实现的逐条对照）：

| 方向 | cmd | 语义 |
|---|---|---|
| 下行 | `1` | 远端弹出了输入框。客户端应聚焦输入控件（官方延迟 **200ms** 再 focus，避开远端 UI 动画抢焦点） |
| 下行 | `2` | 远端收起输入框，客户端收键盘 |
| 上行 | `5 <text>` | 回传文字。官方 `onInput` 发的是**本次新增**的 `e.data`（增量），但输入法 `onCompositionend` 发的是**整串** `this.text`——所以中文拼音上屏时是整串发的 |
| 上行 | `6 1/2/3/4` | 退格 / 回车确认 / 左 / 右（官方由 `keyCode` 8/13/37/39 映射而来） |
| 上行 | `0 <ts>` | 心跳，回显里的 `0 <同一个 ts>` 可用来算往返延迟 |
| 上行 | `11 <ratio>` | 键盘遮挡占比上报（可选） |
| 上行 | `12` | 键盘已收起上报（可选） |

中文**必须整串发**（与官方 `onCompositionend` 一致），不要按字节拆、也不要按
拼音的每个候选字母拆——远端输入框会把每个 `5` 当作一次独立的输入事件，拆开就是乱码。
本项目没有走系统输入法，而是把中文输入整串放在一次 `5` 里发出去。

## 弹键盘时不要销毁视频平面

KMS 视频平面的 zpos 高于小程序合成面，系统键盘弹出来会被画面整个盖住。看起来"把画面
藏一下就行"，但 `render-rectangle` 是**单向棘轮**：缩到 1x1 之后再想放大，只有
"管线过一次 READY 重建"这一条路，而重建后要靠 PLI 求 IDR——实测网关常常不补，
恢复后 `rx=0 frames=0 kf=0`，画面再也回不来。

本项目的解法是**空间上避开**：把输入控件放进画面之外的一栏。

```text
画布 960x266 = 左栏 243（信息） + 中间 473（KMS 挖孔，视频） + 右栏 244（自绘数字键盘）
```

右栏完全在 KMS 平面之外，键盘弹出时视频照常播，玩家能边看边输。手机号/验证码都是
纯数字，数字键盘够用；真要打汉字再走"藏画面 + 系统输入法"的重路径，并接受重建代价。

## 长按 / 滑动 / 点击 三者的区分（设备侧注入工具）

真机自动化用一个 `send_event` 类的工具注入触摸，它的用法是：

```sh
send_event touch press  <x> <y>     # 按下
send_event touch release <x> <y>    # 抬起
send_event touch slip   <x> <y>     # 位移
```

**`slip` 只发一次会被当成点击**（位移太小、时间太短）。正确的滚动是：

```sh
send_event touch press 200 500
send_event touch slip  200 480      # 多次小幅 slip，每次间隔 30ms 左右
send_event touch slip  200 460
send_event touch slip  200 440
send_event touch release 200 440
```

注意 `press` 与 `release` 之间**不要插 `sleep` 超过 1 秒**，否则会变成"长按"语义。

> 触摸事件的取值范围与坐标语义见 [falcon-ui-dialect.md](falcon-ui-dialect.md) 的
> 「触摸事件与坐标」；本机自动化注入的可行性见 [platform-pitfalls.md](platform-pitfalls.md)
> 的「触摸注入与自动化」。本节只讲**怎么把操作送到远端**。

## 症状 → 方向

按排查成本从低到高排。**先做便宜的三件事，再怀疑协议。**

| 症状 | 先查 |
|---|---|
| 点了完全没反应，画面正常 | 日志里有没有 `[T] down` 这类打印？**没有就是 JS 异常**，去抓 `console.warn/error`，看触摸回调第一行还在不在 |
| 有 `down` 打印但远端没反应 | 打印出来的坐标是不是 `0..videoWidth`（像素）？是 `0..65535` 就是单位错了 |
| 坐标是像素但点还是偏 | 三点采样：`pageX == 逻辑x - VIDEO.x`，对不上就漏减/多减了原点 |
| 每个点都落在左上角 | 用了 `clientX`/`offsetX`（不存在 → `NaN` → 兜底成 0） |
| 点了半天只有第一次生效 | 会话已被看门狗拆掉（切后台/弹键盘/长时间息屏）；先确认 session 还活着 |
| 端游点了没反应、界面不动 | 端游必须走 `100/101/102` 鼠标协议，且要 `mousemove → 50ms → mousedown → 50ms → mouseup` 的节奏 |
| 切过输入模式后鼠标事件全丢 | 模式被切到 `keymouse`；固定发 `tochscreen`（官方拼写，少一个 `u`） |
| 远端弹输入框但键盘没出来 / 出来被盖住 | 视频平面 zpos 高于合成面；把输入控件放到画面之外，不要缩平面 |
| 回传文字远端收不到 | `5` 要带空格分段（`"5 " + text`），中文整串发不要拆字节 |
| 用回显判断"没发出去" | 网关对 `1/2/3/8` 不 echo；只能看 `0` 心跳回显和界面语义变化 |
| 用截图 diff 判断"生效了" | 云画面自己就在动（实测不操作也有 74% 变化）；先测基线，再用语义 |
| 以上全排除，怀疑要额外握手/要 DataChannel | 最后一步再看；官方在没有 DataChannel 时回落到同一条 WS，输入帧格式完全一致 |

## 未在此机型验证

- **多点触控**：只用单指验证过；`identifier → slotId` 的映射在真机上最多支持多少指、
  远端是否按 20 槽位分配，未验证。
- **手势缩放**（双指）：协议上是两个 id 同时 `down` + 逐步 `move` + `up`，未在真机验证。
- **PC 键盘**（`104`/`105`）：只验证了触摸与鼠标，键盘码表未逐键验证。
- **`cmd "11"` / `cmd "12"`**（键盘遮挡上报）：实现了但从未被远端要求过，未验证必要。
